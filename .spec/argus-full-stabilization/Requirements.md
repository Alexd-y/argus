# ARGUS — Полная стабилизация (Requirements)

Связанная спецификация: [.spec/argus-profile-orchestration-rework](../argus-profile-orchestration-rework/) —
данная спецификация продолжает и стабилизирует результат того рефакторинга
(коммиты `50f8841`, `737c3b9`), не дублируя его.

## Введение

После массового `ruff`-рефакторинга (`50f8841`) и точечных фиксов (`737c3b9`)
часть тестов не запускалась из-за отсутствия живых зависимостей (PostgreSQL,
Redis, MinIO) и из-за реальных дефектов в миграциях и тестовой инфраструктуре.
Цель — привести backend к состоянию «0 failed, 0 errors» на реально поднятом
контейнерном стенде зависимостей, устранить утечки состояния между тестами,
подтвердить контракты ARGUS (scan-профили, отчёты, реестры инструментов),
подготовить код к переносу на AWS (без развёртывания) и зафиксировать результат.

## Глоссарий

- **Validation stack** — изолированный Docker Compose проект `argus-validation`
  (собственные тома/порты), поднимающий PostgreSQL (pgvector), Redis, MinIO для
  локального прогона тестов. Не пересекается с продакшн-стеком `argus-*`.
- **Layer A / Layer B тесты миграций** — Layer A: диалект-независимые проверки
  метаданных ревизии (без БД); Layer B: round-trip против живого PostgreSQL,
  включаемый при `DATABASE_URL`, указывающем на Postgres.
- **RLS** — Row Level Security PostgreSQL; `FORCE ROW LEVEL SECURITY` подчиняет
  политике даже владельца таблицы.
- **Order-dependent flakiness** — падение теста, зависящее от порядка исполнения
  из-за общей (глобальной) изменяемой конфигурации/реестра/соединения.

## Требования

### R1. Изолированный контейнерный стенд зависимостей
- КОГДА тесту нужны PostgreSQL/Redis/MinIO, ТО система ДОЛЖНА поднимать их в
  отдельном Compose-проекте `argus-validation` с disposable-томами и не
  затрагивать продакшн-тома `argus-*`.
- Критерии: `docker compose -p argus-validation ... config` без ошибок; все
  сервисы `healthy`; PostgreSQL принимает соединения; Redis отвечает `PONG`.

### R2. Alembic — единственный линейный head, чистый round-trip
- КОГДА выполняется `alembic upgrade head` на чистой БД, ТО система ДОЛЖНА
  довести схему до последней ревизии без ошибок.
- КОГДА выполняется `alembic downgrade base` из head, ТО система ДОЛЖНА
  корректно откатить всю цепочку (в т.ч. смену первичного ключа
  `admin_sessions.session_token_hash`) без ошибок PostgreSQL.
- КОГДА проверяется число heads, ТО система ДОЛЖНА иметь ровно один head; тест
  НЕ ДОЛЖЕН завязываться на конкретный номер ревизии.

### R3. PostgreSQL-специфичные и RLS-тесты реально исполняются
- КОГДА `DATABASE_URL` указывает на живой Postgres, ТО Layer B тесты миграций,
  RLS и pg-специфичные проверки ДОЛЖНЫ запускаться и проходить.
- КОГДА сессия задаёт `app.current_tenant_id`, ТО арендатор A НЕ ДОЛЖЕН видеть
  строки арендатора B (в т.ч. под `FORCE RLS`), а запись с чужим/пустым
  tenant ДОЛЖНА отклоняться `WITH CHECK`.

### R4. Изоляция состояния между тестами
- КОГДА тест миграций отработал, ТО общая тестовая БД ДОЛЖНА возвращаться к
  `base` (или иному детерминированному состоянию), чтобы следующий тест не видел
  чужую схему.
- КОГДА тесты sandbox-парсеров/alembic исполняются в полном наборе, ТО результат
  НЕ ДОЛЖЕН зависеть от порядка.

### R5. Повторная проверка 7 прежних фиксов + regression tests
- КОГДА проверяется каждый из 7 фиксов (redaction, usage_ledger, LAB auth,
  coverage write-back, tool-name extraction, source-code regex, single-head), ТО
  ДОЛЖЕН существовать regression-тест, воспроизводящий исходный дефект и
  подтверждающий фикс, включая негативные/граничные случаи.
- LAB authorization: непустой `lab_allowed_targets` сам по себе НЕ ДОЛЖЕН
  авторизовывать произвольный target; требуются lab_unrestricted + активный
  lease нужного tenant/engagement + target в scope + kill-switch off.
- usage_ledger: событие учёта НЕ ДОЛЖНО молча теряться при отсутствии event loop.

### R6. Контракты ARGUS не сломаны
- Внешние профили ровно `quick|light|deep` с фиксированным маппингом; `deep`
  требует активный LAB lease; конфликт профиля/legacy-полей → 422.
- Отчёты Quick/Light/Deep формируются в PDF/JSON/MD/XML из единого immutable
  snapshot; AI не добавляет findings/CVE/endpoints/exploitability без evidence.

### R7. AWS-переносимость (без развёртывания)
- Все внешние endpoints конфигурируются через env; нет обязательного hardcoded
  localhost; S3-абстракция совместима с AWS S3 (path/virtual-hosted); секреты не
  в образах/репозитории; backend/worker stateless; есть health/readiness и
  graceful SIGTERM. Реальные облачные ресурсы НЕ создаются.

### R8. Отсутствие секретов/артефактов в коммите
- КОГДА выполняется commit, ТО в индекс НЕ ДОЛЖНЫ попадать `.env`, дампы,
  тома, логи, токены, ключи, AWS-креды или несвязанные артефакты.

## Свойства корректности

1. `upgrade base→head→base` идемпотентен и не оставляет мусора в схеме.
2. Ни один тест не зависит от локальной dev-БД разработчика.
3. Ни один фикс не «прячет» дефект (нет fail-open, silent no-op, ослабления
   security-assert, замены ожидаемого значения ради зелёного прогона).
4. Каждый устранённый баг покрыт regression-тестом.

## Простое объяснение

Мы поднимаем настоящие «батарейки» (БД, кеш, файловое хранилище) в отдельной
песочнице Docker, прогоняем на них тесты, чиним реальные баги миграций и
тестов, следим, чтобы тесты не «пачкали» друг друга общим состоянием, и
подтверждаем, что ключевые правила ARGUS (профили сканирования, отчёты,
безопасность LAB) по-прежнему выполняются — не ослабляя ни одной проверки.
